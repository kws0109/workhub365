화면

실제 Microsoft 365 테넌트에 연결한 상태에서 촬영했습니다. 라이브 URL은 Entra SSO 전용이라 외부 계정으로는 로그인할 수 없어, 아래 캡처로 대신합니다.

승인 게이트 — AI에게 무엇을 못 하게 할 것인가

계정 차단·삭제, 라이선스 회수, 세션 철회, 그룹 제거는 AI가 직접 실행할 수 없습니다. 게이트를 도구마다 분기로 넣는 대신 실행 진입점 하나에 구조로 강제했습니다 — 도구가 늘어도 불변식이 유지되고, 외부 MCP 클라이언트가 붙어도 변경 액션은 실행되지 않습니다.

  1. 사용자가 자연어로 요청하면 모델이 도구 호출을 결정한다
  2. 도구는 승인 없이는 실행되지 않고 approval_required를 반환한다
  3. 승인 요청이 저장된다 — 멱등 키는 도구 호출 id, 만료는 15분
  4. 대상 GUID를 Graph로 조회해 사람이 읽을 이름으로 바꿔 카드에 표시한다. 승인자가 무엇을 승인하는지 알 수 없으면 게이트는 형식일 뿐이다
  5. 관리자가 승인하면 조건부 UPDATE로 클레임한다 — 두 탭에서 동시에 눌러도 정확히 1회만 실행된다
  6. 실행 결과와 승인자가 감사 로그에 남는다

주요 의사결정

전체 목록과 근거는 리포의 설계 문서에 있습니다.

결정이유
계정 식별을 이메일이 아닌 불변 클레임 oid로 이메일은 재활용된다 — 퇴사자 주소를 새 입사자가 받으면 권한을 상속받는 문제를 차단
동시성 불변식은 앱 락이 아닌 DB에서 조건부 UPDATE와 유니크·EXCLUDE 제약으로 강제 — 서버리스 다중 인스턴스에서도 성립한다
인사 권한을 역할이 아닌 직교 플래그로 결재 서열과 업무 자격은 축이 다르다. 역할 하나로 묶으면 인사팀 매니저가 결재권을 포기해야 한다
쓰기 UX는 딥링크로 위임 메일 답장·파일 업로드를 M365로 넘겨 요청하는 권한 범위를 최소화. 예외는 회의실 예약 하나
위임 토큰을 세션 응답에 싣지 않음 브라우저로 토큰이 내려가는 경로를 차단하고 서버 전용으로만 복호화

어떻게 만들었나

코드 생성은 AI 코딩 에이전트가 했고, 스펙 결정·검증·반려 판단은 사람이 했습니다. 무엇을 왜 반려했는지가 리포에 기록으로 남아 있습니다.

스펙이 먼저

요구사항·설계·작업 문서를 진실의 원천으로 두고, 구현이 스펙과 달라져야 하면 스펙을 먼저 고쳤습니다. 코드 주석의 요구사항 번호가 문서의 항목과 그대로 이어집니다.

에이전트 산출물을 그대로 받지 않음

한 리뷰에서 19건이 지적됐지만 하나씩 확인한 뒤 13건만 반영했습니다. 설계안 세 개를 경합시켰을 때는 셋 다 놓친 우회 경로 4종이 심사에서 드러났습니다.

코드만으로는 안 보이는 것

페이지가 몇 분씩 멈추는 문제를 직접 계측해 원인을 찾았습니다 — 권한 오류 뒤 토큰 재발급이 응답 없이 매달렸고, 그 하나가 막히자 모든 호출이 대기하고 있었습니다.

알면서 남긴 것도 기록

구현하지 않기로 한 한계와 후속 과제를 파일·줄 단위로 문서에 남겼습니다. 무엇을 만들었는지만큼 무엇을 알면서 남겼는지가 중요하다고 봤습니다.

알려진 한계

  • 공유 메일박스 전환은 Graph API가 지원하지 않아 오프보딩에서 제외했습니다
  • 마지막 로그인 시각은 상위 라이선스가 필요해, 없는 테넌트에서는 "알 수 없음"으로 표시됩니다
  • Teams 채팅 본문 등 별도 승인이 필요한 API는 사용하지 않습니다
  • 회의실 예약은 테넌트에 리소스 사서함과 해당 권한이 있어야 활성화되며, 없으면 안내 카드로 대체됩니다
  • 어시스턴트 대화는 서버에 저장하지 않습니다 — 새로고침하면 초기화됩니다
