# 프롬프트 로그

AI 페어 프로그래밍으로 구현한 작업마다 **[근거 스펙 + 실행 프롬프트 + 왜 그렇게 물었나]**를 기록한다 (N6 투명성).
목적: 대화 히스토리가 없는 새 세션(또는 제3자)이 이 로그만 보고 ① 무엇을 근거로 ② 어떤 지시로 ③ **왜 그런 지시로** 구현됐는지 재현할 수 있게 한다.

에이전트 주도 개발에서 **재현 가능한 것은 코드가 아니라 지시**다. 같은 프롬프트라도 왜 그렇게 물었는지를 모르면 다음 상황에 응용할 수 없어서, 각 항목에 **"왜 이렇게 물었나"**를 함께 남긴다.

**읽는 순서 — 시간이 없다면 이 셋부터.** AI에게 맡긴 결과를 그대로 받아쓰지 않고 검증했다는 증거가 몰려 있는 항목이다.

1. [Phase 8](#2026-08-09--phase-8-인사hr-근태휴가-정정) — 설계안 3종을 경합시키고 3렌즈로 심사하자 **세 안 모두가 놓친 구멍 4종**이 드러났다. 단일 설계안이었으면 전부 통과했을 것들
2. [Phase 5](#2026-08-09--phase-5-m5-ai-어시스턴트-mcp-도구--승인-게이트) — 병렬 리뷰 **지적 19건을 반박 검증해 고유 결함 13건으로 정리**. 리뷰 지적을 건수로 받아들이지 않고 하나씩 검증해 가려낸 기록
3. [Phase 7](#2026-08-09--phase-7-디자인-개편--m8-협업-전체-b1b17) — 코드 리뷰로는 안 나오고 **실측으로만 잡힌 결함**: 고착된 소켓 뒤에서 페이지가 5~7분 멈추던 문제 → Graph 클라이언트 전체 15초 타임아웃

- **짝 문서**: 이 문서는 *어떤 지시로* 만들었는지를 남기고, [review-log.md](review-log.md)는 *그 결과물이 무엇을 지적받고 무엇을 채택했는지*를 남긴다. 리뷰 10회·지적 216건의 원문과 채택·기각 근거가 그쪽에 있다
- 형식: 항목당 [날짜 / 작업 / 근거 스펙 / 실행 프롬프트 / **왜 이렇게 물었나** / 결과 커밋]. 프롬프트는 실제 사용한 문구를 그대로 인용한다
- 2026-08-09 이전 항목은 세션 기록(transcript)에서 **소급 발췌·복원**한 것이다. 원문 인용이 원칙이며, "(요약)" 표기가 붙은 것만 공개 문서에 맞게 맥락을 요약·일반화했다
- 짧은 지시("Phase N 진행해줘")로 큰 작업이 진행된 것은 스펙 주도 개발의 결과다 — 상세 요구는 [specs/](specs/)가 대신하고, 프롬프트는 트리거 역할만 한다

## 질문 설계 원칙 8

개발 과정에서 반복해 쓴 원칙이다. 각 항목의 "왜 이렇게 물었나"가 이 중 하나를 가리킨다.

| # | 원칙 | 왜 필요한가 |
|---|---|---|
| 1 | **스펙이 본문, 프롬프트는 트리거** | 상세를 프롬프트에 넣으면 대화가 사라지는 순간 재현이 불가능해진다 |
| 2 | **넘기지 않을 선을 먼저 못 박는다** | 에이전트는 요구하지 않은 안전장치를 스스로 만들지 않고, 빈칸은 임의로 채운다 |
| 3 | **진도보다 정합성** | 리뷰 반영 전에 다음 단계로 가면 결함 위에 결함이 쌓인다 |
| 4 | **증상이 아니라 근본을 요구한다** | 에이전트는 지시한 증상만 고치는 경향이 강하다 |
| 5 | **미래 조건을 걸고 검토시킨다** | 현재 조건에서는 재현되지 않는 결함이 있다(동시성이 대표적) |
| 6 | **지적을 우선순위로 잘라 채택한다** | 리뷰 지적을 건수로 받으면 복잡도만 늘어난다. 지적은 가설이지 결론이 아니다 |
| 7 | **하나의 산출물을 믿지 않는다** | 단일 설계안은 자기 전제의 구멍을 못 본다 |
| 8 | **컨텍스트를 자원으로 관리한다** | 세션이 길어지면 품질이 떨어지고, 대화에서만 아는 맥락은 정리하지 않으면 증발한다 |

### 원칙 7의 빈틈 — 열지 않은 축

기록해 둘 한계가 있다. **원칙 7을 제품 선택에는 적용했으나 구현 방식 선택에는 적용하지 않았다.**

Phase 0에서 물은 것은 *"제품 후보를 복수로 제안해 달라"*였고, **구현 방식(프레임워크·플랫폼) 후보는 묻지 않았다.** 에이전트는 물어본 축에서만 선택지를 열기 때문에, Next.js는 비교 과정 없이 전제로 깔린 채 진행됐다 — `ca1c107` 커밋 본문에도, [design.md](specs/design.md)에도 선정 근거가 없다. 같은 이유로 SharePoint Framework(SPFx)나 Power Platform 같은 M365 네이티브 구현 방식은 후보에 오른 적이 없다.

교훈은 **"복수로 제안해 달라"만으로는 부족하고, 어떤 축에서 복수인지를 명시해야 한다**는 것이다. Phase 8에서 설계안 3종을 경합시킨 것이 뒤늦게 같은 원칙을 구현 방식에 적용한 사례다.

- **보조 프롬프트 (원문)**: "E3는 안됨?" — 평가판 테넌트 선택 논의 → Microsoft 365 E3(Entra P1 포함)로 결정해 셋업 가이드에 반영
- **왜 이렇게 물었나**:
  - **답이 아니라 선택지를 요구했다(원칙 7)** — "이런 걸 만들어줘"로 물으면 에이전트는 그럴듯한 첫 안을 내고 끝난다. 비교 대상이 있어야 "왜 그걸 골랐는가"가 남는다. 이 질문이 "국내에 M365 전용 관리도구가 사실상 공백"이라는 선정 근거를 만들었다
  - **외부 의존의 제약을 코드보다 먼저 확인했다** — "E3는 안됨?"은 짧지만 결정적이었다. Microsoft 365 E3는 Entra P1을 포함해 `signInActivity`(마지막 로그인)를 읽을 수 있지만 Office 365 E3는 못 읽는다. 이건 라이선스 낭비 계산의 핵심 입력이라, 구현 후에 알았다면 기능 하나가 통째로 무너졌다. 에이전트는 "일단 만들고 나중에" 쪽으로 흐르므로 전제 조건은 사람이 먼저 확인해야 한다
  - **이 단계의 진짜 산출물은 코드가 아니라 규칙이다(원칙 2)** — CLAUDE.md의 아키텍처 규칙 6조, 특히 규칙 3(되돌리기 어려운 액션은 승인 게이트 필수)은 **금지 조항**이다. 에이전트는 "AI가 계정을 차단하게 해줘"라는 요구를 받으면 가장 짧은 경로로 구현하지, 승인 게이트를 스스로 만들지 않는다. 제품을 만들기 전에 규칙으로 박았기 때문에 Phase 5의 승인 게이트가 "나중에 붙인 안전장치"가 아니라 처음부터 구조로 들어갔다
- **결과 커밋**: `ca1c107` 스캐폴드, `3af8219` 스펙 문서, `76b4370` Phase 0 완료, `04a01be` E3 대안

**왜 이렇게 물었나**:

- **"근본 문제를 해결"이라는 다섯 글자(원칙 4)** — 캘린더에서 19일은 안 보이고 20일은 보이는 현상이 있었다. "19일도 보이게 해줘"라고 했다면 에이전트는 **그 케이스만** 고쳤을 것이고 다음 조합에서 또 터졌을 것이다. 명시적으로 근본 해결을 요구하자 레인 배정과 펼치기를 **셀 단위에서 주(week) 단위로 재설계**하는 답이 나왔다. 셀 단위로 펼치면 여러 날에 걸친 휴가는 구조적으로 끊길 수밖에 없다는 것이 문제의 실체였다
- **성능은 숫자로 닫았다** — "느리다"만으로는 검증이 안 된다. 측정해 보니 원격 DB 왕복(~200ms)이 페이지마다 5~9회 **직렬** 실행되는 것이 병목이었다. 수정 후 전/후를 실측해 커밋 본문에 남겼다(/leave 1733→561ms 등). "빨라졌습니다"는 결과가 아니다
- **도메인 판단은 넘기지 않았다** — "시작일을 종료일 이후로 설정하면 못하도록"에는 숨은 선택이 있다. 자동 보정(종료일을 따라 올림)은 사용자가 모르는 사이 **기간이 늘어난다.** 휴가는 잔여 연차가 차감되는 행위라 조용히 늘어나면 안 된다. 그래서 보정이 아니라 **거부**를 지시했다. 같은 맥락에서 주말·휴일 셀은 클릭 자체가 불가능하게 만들어(`c44af6c`) 검증 메시지가 아니라 **UI 구조로 원천 차단**했다
