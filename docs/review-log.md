# 리뷰 로그

[prompt-log.md](prompt-log.md)가 **어떤 지시로** 만들었는지를 남긴다면, 이 문서는 **그 결과물이 무엇을 지적받았고 무엇을 채택했는지**를 남긴다.

이 리포는 1인 개발이라 PR 리뷰 스레드가 없다. 대신 커밋 직전에 관점(렌즈)을 나눈 병렬 에이전트 리뷰를 돌리고, 지적을 선별해 반영한다([CLAUDE.md](../CLAUDE.md) 스펙 주도 개발 절). 그 리뷰가 PR 스레드를 대신하는 기록인데, 그동안 커밋 본문에는 **채택 결과만** 남고 원본 지적과 기각 근거는 남지 않았다. 이 문서가 그 공백을 메운다.

- 출처: 세션 기록의 워크플로 저널(`journal.jsonl`)과 서브에이전트 대화. 지적 문구는 원본 요약이다
- 각 항목은 [실행 시각 / 트리거 / 렌즈 구성 / 지적 건수 / 대표 지적 / 채택 결정 / 결과 커밋] 순이다
- 채택하지 않은 지적도 남긴다. 무엇을 버렸는지가 무엇을 골랐는지만큼 판단을 보여준다

## 크리티컬 — 계정 탈취 경로 (nOAuth 패턴)

> Account identity is keyed on the mutable Entra 'email' claim with no verification that the incoming 'oid' matches the stored one.

사용자를 이메일로 식별했다. Entra의 이메일은 바뀔 수 있고 테넌트 밖에서도 같은 값을 주장할 수 있다. **세 렌즈가 전부 이 문제를 각각 지적했다.**

같이 나온 fail-open 경로 두 개도 두 렌즈씩 겹쳤다.

- `AUTH_MICROSOFT_ENTRA_ID_ISSUER`가 비면 기본 발급자가 멀티테넌트 `/common`이 되어 **지구상 아무 Microsoft 계정이나 로그인**된다
- DB에서 사용자 행이 지워져도 JWT의 이전 `dbId`/`role`이 최대 30일 유지된다. `if (row)` 하나가 fail-open을 만들었다

## 그 외

- `drizzle-orm/neon-http`는 대화형 트랜잭션을 지원하지 않는데 `db.transaction`을 쓰고 있었다
- 401 토큰 재발급 재시도가 429/503 스로틀 재시도와 같은 카운터를 공유한다
- `Retry-After` 대기에 상한이 없어 서버리스 실행 시간을 넘길 수 있다
- 재시도 경로에서 응답 본문을 소비하지 않아 undici 소켓이 샌다
- `getAppToken`에 in-flight 중복 제거가 없어 콜드스타트에서 동시 요청이 각각 AAD를 친다

## 채택

전면 수정했다. `oid`(entraId) 기준 식별로 바꾸고 발급자를 명시해 fail-closed로 만들었으며, 드라이버를 `neon-serverless`로 교체했다. 결정 근거는 [design.md](specs/design.md) 인증 절에 별도로 기록했다.

**결과 커밋**: `1fa4ad9` (design.md에 oid 키잉·fail-closed·드라이버 결정 기록), Phase 1 전반

# 3. Phase 3 온·오프보딩 (08-08 00:52)

- **트리거**: 위와 같은 흐름
- **렌즈 2개**, **지적 17건** (9 + 8). 크리티컬 2건이 나왔고 **두 렌즈가 같은 것을 지목했다**

## 크리티컬 ① 실패했는데 성공으로 보고한다

> An unrecognized `resumeFrom` makes runPipeline skip every step and return `{ ok: true }`.

알 수 없는 `resumeFrom` 값이 들어오면 모든 단계를 `skipped`로 넘기고 성공을 반환한다. 계정 차단, 세션 철회, 라이선스 회수가 **하나도 실행되지 않았는데 화면에는 완료로 뜬다.**

동작이 정상이었기 때문에 실행 테스트로는 드러나지 않는 종류다. 파괴적 파이프라인에 리뷰를 절차로 넣어야 하는 이유가 여기 있다.

## 크리티컬 ② 임시 비밀번호 유실

> The temp password is discarded and never shown whenever onboarding does not fully succeed on the first attempt.

`result.ok && !resumeFrom`일 때만 비밀번호를 반환한다. 부분 실패하면 계정은 만들어졌는데 아무도 비밀번호를 모른다. 이 결함은 나중에 Phase 5 어시스턴트의 `create_user`에서 **같은 형태로 재발**했고, 그때는 이 lifecycle 경로의 방어 코드가 "의도된 트레이드오프가 아니다"라는 판정 근거가 됐다.

## 그 외

- 그룹 추가/제거가 멱등하지 않다. 재시도하면 이미 속한 멤버에 400이 나고 중간에 멈춘다
- 오프보딩이 대상의 라이선스·그룹 정보를 파괴하면서 감사 로그에는 **건수만** 남긴다. 복구가 불가능해진다
- 클라이언트가 보낸 `createdUserId`를 검증 없이 신뢰해서, 온보딩 resume 경로가 임의 사용자에게 라이선스를 부여하는 통로가 된다
- 자기 자신 오프보딩 차단 가드가 대소문자 구분 문자열 비교라 우회된다

## 채택

8건. `resumeFrom` 검증, 부분 실패 시에도 비밀번호 전달, 그룹 작업 멱등화가 핵심이었다.

**결과 커밋**: `5a58af3` 온보딩/오프보딩 파이프라인 (실테넌트 E2E 검증 완료)

## 왜 이 리뷰를 지시했나

혼자 쓰는 앱에서는 동시성 결함이 **재현되지 않는다.** 테스트로도 실행으로도 안 나온다. 현재 조건이 아니라 미래 조건(전사 사용)을 걸어야 그 코드 경로가 검토 대상이 된다.

## 대표 지적

- `createLeave`의 겹침 가드가 check-then-insert **TOCTOU**이고 뒤를 받치는 DB 제약이 없다
- `decideLeave`의 겹침 재검사는 **커밋된 행만** 본다. READ COMMITTED에서 두 결재자가 동시에 승인하면 서로의 미커밋 행을 못 보고 둘 다 통과한다
- neon-serverless Pool에 `error` 리스너가 없다. 유휴 소켓 에러 하나가 **프로세스를 죽인다**
- 라이프사이클 라우트가 "클라이언트가 끊겨도 파이프라인은 계속된다"고 주석에 적어놓고 실제로는 보장하지 않는다
- `bustGraphCache`가 `store`만 비우고 `inflight`는 놔둔다. 변경 직전에 시작된 조회가 **낡은 값을 다시 캐시에 채운다**
- `audit_logs`에 단조 증가 컬럼이 없다. PK가 랜덤 UUID고 `createdAt`은 동시 쓰기에서 순서를 보장하지 않는다
- `updateSkuPrice`가 이전 값을 트랜잭션 **밖에서** 읽어 감사 로그의 before 값이 틀릴 수 있다

## 채택 결정

사용자가 범위를 **"필수 + 저비용 권장"** 으로 잘랐다. 커밋 본문은 이렇게 묶었다.

**필수**

| 항목 | 조치 |
|---|---|
| 겹침 휴가 TOCTOU + 동시 승인 | **EXCLUDE 제약**(btree_gist, 활성 상태 한정)으로 DB가 원천 봉쇄. 23P01을 친화적 오류로 매핑 |
| DB 풀 | `error` 리스너, idle/connection 타임아웃 명시, 풀러(`-pooler`) 요구 문서화 |
| 라이프사이클 스트림 | `after()`로 클라이언트 취소 시에도 완주 보장 + `maxDuration` 명시 |

**저비용 권장**

오프보딩 라이선스 회수 멱등화, `audit_logs` 단조 순번(`seq`), `bustGraphCache`가 `inflight`도 정리, 공휴일 API 5초 타임아웃 + 실패 시 10분 백오프, 디렉터리·그룹 조회 페이지 상한 통일, 단가 이전 값을 트랜잭션 안에서 읽기.

**버린 것**: `info` 등급의 구조 관찰 몇 건. 당장 재현되지 않고 비용이 큰 것들이다.

> 사용자 프롬프트의 "필수 4건"과 커밋 본문의 필수 3항목은 묶는 단위가 달라서 생긴 차이다. 리뷰 산출물의 분류를 커밋에서 주제별로 합쳤다.

# 6. M6 기안 (08-09 01:08)

- **렌즈 2개**, **지적 9건** (4 + 5)

## 대표 지적

- `cancelProposal`의 "아직 아무도 결재 안 함" 검사와 실제 회수 사이에 **TOCTOU**가 있다. 회수와 최종 승인이 겹칠 수 있다
- 상세 화면이 **현재 템플릿의 필드 목록**으로만 내용을 렌더한다. 템플릿이 바뀌면 과거 기안의 내용이 화면에서 사라진다
- 결재자가 퇴사하면 그 기안은 영구히 `in_progress`에 갇힌다. 탈출구가 없다
- `DATE_RE`가 형식만 본다. `2026-02-31`, `2026-13-45`가 통과한다

## 한 렌즈가 지적을 스스로 취소했다

> The suspected operator-precedence bug is NOT present — `a || b && c` groups as `a || (b && c)`, and both possible groupings are equivalent here.

의심 지점을 검토한 뒤 **결함이 아니라고 명시적으로 결론**냈다. 리뷰 산출물에 "아닌 것"도 남긴 사례다.

## 채택

`DATE_RE` 지적은 기안 경로만 고쳤다. **이 판단이 뒤에서 되돌아온다** (아래 10번 참조).

## 왜 이 리뷰를 지시했나

Phase별 리뷰는 그 Phase의 변경분만 본다. 여덟 단계를 거치는 동안 **화면 사이의 상호작용과 반복된 패턴**은 아무도 통으로 보지 않았다. 제출 직전에 범위를 리포 전체로 넓힌 이유다.

## 종합 단계가 중복을 묶었다

39건 중 상당수가 같은 뿌리였다. 종합 에이전트가 이렇게 정리했다.

- *"날짜·월 쿼리 파라미터를 '모양'만 검사하고 실재성을 검사하지 않아 3개 화면이 자기유발 500으로 죽는다 (**6건 중복의 단일 근본원인**)"*
- *"휴가 기간에 상한이 없어 이벤트 루프 수 초 정지 + 병가 경로에서 numeric(4,1) 오버플로 (**3건 중복의 단일 근본원인**)"*

## 가장 값나간 발견

**3번, 조직도의 병가 노출.**

`/leave`는 휴가 정보를 부서 범위로 좁혀둔 화면인데, 조직도 배지가 휴가 **유형을 그대로 문구로** 써서 전 직원에게 병가가 이름표로 보이고 있었다. 스펙 R8.3 위반이자, 의도적으로 막아둔 정보의 우회 경로다.

기능은 정상 동작했다. 화면도 멀쩡했다. 실행 테스트로는 절대 안 나온다.

조치는 유형 무관 '휴가' 단일 문구로 바꾸고 **쿼리에서 `type` 컬럼 자체를 제거**했다(최소 수집). 실브라우저에서 오늘자 승인 병가를 만들어 조직도가 '휴가'로만 표시하는 것을 확인하고 정리했다.

## 2번의 부수 발견

`countLeaveDays` 루프에 상한이 없어 9999년 종료일이면 **291만 회 루프로 이벤트 루프가 4초 동기 블로킹**됐다. 서버리스에서는 한 프로세스가 여러 요청을 나르므로 동거 요청까지 함께 멈춘다. 실측 3,945ms → 0.073ms.

수정하면서 구조 결함도 하나 닫았다. 기간 상한 가드가 `if (type !== 'sick')` 블록 **안쪽**에 있어서 병가가 상한을 통째로 우회하고 있었다. 가드를 조건문 밖으로 빼고, DB CHECK(`leave_days_range`)도 추가해 앱을 우회한 경로는 23514로 거부하게 했다.

# 리뷰가 리뷰를 잡은 사례

M6 기안 리뷰(08-09 01:08)가 `DATE_RE`의 형식-검사 문제를 **minor**로 올렸다. `2026-02-31`이 통과한다는 지적이었고, 그때는 **기안 경로만** 고쳤다.

21시간 뒤 최종 전체 리뷰가 같은 근본원인이 `/calendar?week=`, `/rooms?date=`, `/leave?month=` 세 화면에 그대로 남아 있는 것을 찾았다. 세 갈래로 다르게 터졌다.

| 화면 | 증상 |
|---|---|
| `/calendar` | `toISOString` RangeError |
| `/rooms` | 헤더 JSX 조립 시점 평가라 try/catch로도 못 막힘 |
| `/leave` | `monthStart` 조립이 Postgres 22008 |

조치는 `date-param.ts` 신설이었다. `isCalendarDate`는 라운드트립 비교로 `2026-02-31` 롤오버까지 차단하고, `isCalendarMonth`는 연도를 2000~2100으로 제한한다(공휴일 외부 API 연도로 흘러가므로 상한이 필요하다).

**교훈은 범위다.** 지적을 발견된 자리에서만 고치면 같은 결함이 리포 안에 남는다. minor 등급이라 우선순위가 낮았던 것도 사실인데, 그래서 더더욱 "이 패턴이 다른 곳에도 있나"를 묻는 단계가 필요했다.

# 이 문서가 남기는 것

1. **에이전트 리뷰는 지적을 과잉 생산한다.** 216건 중 채택은 절반 남짓이다. 그대로 반영하면 복잡도만 늘어난다
2. **렌즈를 나누면 겹친다.** Phase 1은 3렌즈가 같은 크리티컬을 각각 찾았고, Phase 5는 19건 중 6쌍이 중복이었으며, 최종 리뷰는 39건이 근본원인 7개로 접혔다. 겹침은 낭비이면서 동시에 **독립 관측이 일치했다는 신호**다
3. **리뷰가 못 잡는 층이 있다.** Phase 7의 5~7분 페이지 정지는 리뷰가 전부 통과한 코드에서 실측으로 나왔다. single-flight도 401 재발급도 각각은 정상 로직이고, 둘이 겹치고 소켓이 죽어야만 나타난다
4. **범위를 넓히는 것 자체가 판단이다.** 사용자가 지정한 두 리뷰(동시성, 최종 전체)가 각각 TOCTOU와 병가 노출을 잡았다. 둘 다 "지금 이 코드"가 아니라 "다른 조건에서의 이 코드"를 물은 결과다
